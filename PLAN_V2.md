### 0.2. Что забрать из соседних репозиториев

**`IDM-DTCal`** — уже содержит рабочие, **проверенные вживую** конфиги
мультиметров в режиме **вольтметра**. Это готовый фундамент для п. 4:

- `akipb778.json` — шкалы DCV **0.1/1/10/100/1000 В** (платформа Agilent 34401A).
  В комментарии прямо описан баг: раньше стоял чужой массив 0.2/2/20/200/1000,
  из-за чего запрос диапазона 20 В прибор округлял вверх до 100 В и терял
  разрешение. **Это прямая иллюстрация к п. 6** — неверный массив `ranges`
  ломает ручное ранжирование молча, без ошибок.
- `rigol_dm3068.json` — **ключевая находка**: DM3068 ручной диапазон
  поддерживает, просто через другую подсистему. Не `SENS:...RANG {value}`, а
  `:MEASure:VOLTage:DC {index}` — **индексом шкалы (0..4)**, и эта команда сама
  уводит прибор в Manual. Авто — `:MEASure AUTO`. То есть наш вывод в v1.4ae
  «DM3068 не умеет ручной диапазон» был неполным: он не умеет *нашего
  синтаксиса*. В v2 конфиг должен поддерживать оба стиля (`{range_val}` и
  `{index}`).

**`IDM-DNKMetr`** — README это подробный отчёт о вводе стенда в эксплуатацию.
Оттуда для п. 5 (источник напряжения GPP-4323):

- Подключение — **не USB-TMC, а ASRL (COM), 115200 8N1**, и только после
  установки вендорского драйвера GW Instek (устройство vendor-specific
  `VID_2184&PID_0057`, обычный CH341SER не подходит, Код 28 в диспетчере).
- **Включение выхода — `ALLOUTON`/`ALLOUTOFF`, проверено вживую.** У нас в
  `instruments/voltage_sources/gpp74323.json` в качестве `output_on` стоит
  `":OUTPut{ch}:STATe ON"` — не проверено ни разу. `ALLOUTON`/`ALLOUTOFF` в
  нашем конфиге лежат рядом, но код их не использует. **Вероятнее всего именно
  это и есть причина, по которой промеры датчиков напряжения не работают.**
- `VOUT1?`/`IOUT1?` отвечают **с суффиксом единиц** (`"00.000V"`, `"0.0000A"`) —
  голый `float()` на таком ответе падает, нужен парсер числа регуляркой.
  У нас readback вообще не реализован, но при добавлении сразу сломался бы.
- Потолок 64 В паспортный, рабочий ограничитель в DNKMetr — **60 В**.
- Долгое нажатие F6 на передней панели отключает дистанционное управление;
  только один интерфейс (USB/RS-232/LAN) активен одновременно.

**`IDM-DTCal`, релиз `v1.1-bipolar-fix`** — для п. 31 и п. 35: биполярная
выходная характеристика `OutputScale(v_minus, v_zero, v_plus)`, кусочно-линейная
с изломом в нуле, нормировка погрешности на **размах** `V_plus − V_minus`.

### 0.3. Разбор бага ручного ранжирования (п. 6) — найден, и он не один

`instruments.py:56-83`, `Multimeter.auto_range()`. Пять дефектов:

1. **Диапазон выбирается по ПРЕДЫДУЩЕЙ точке.** `measurement.py` вызывает
   `dmm.auto_range(i_avg)` *после* измерения точки N, и результат применяется
   к точке N+1. На шаге 0→50 А (датчик 1:2000, ~25 мА) диапазон, подобранный
   под нулевой ток, физически не годится. Это первопричина `9·10³⁸`
   ([issue #3](https://github.com/alexlegoshin/IDM-IVTrace/issues/3)).
2. **Подъём только на одну ступень за точку** (`current_range_idx += 1`).
   Даже поймав переполнение, алгоритм не может догнать за один шаг —
   с 200 мкА до 20 мА это 2 точки мусора подряд.
3. **Сентинел переполнения скармливается обратно в алгоритм.** `9.9e37`
   приходит в `auto_range()` как «измеренный ток» — состояние диапазона
   после этого бессмысленно. Нет проверки `abs(v) > 1e30`.
4. **Гистерезис задан так, что провоцирует автоколебания.** Подъём при >95%
   предела, спуск при <10%. На декадных шкалах 10% диапазона N — это ровно
   100% диапазона N−1, то есть сразу >95% → колебание вверх-вниз на границе.
5. **Нет паузы после смены диапазона** — прибор физически переключает реле
   входного делителя и не успевает устояться. Отсюда требование п. 6 о
   задержке 0.7 с.

Плюс шестое, конфигурационное: неверный массив `ranges` ломает всё молча
(см. историю DTCal выше).

## 1. Решения по спорным местам ТЗ

Все пять вопросов заданы заказчику и **закрыты** (согласовано 2026-08-05).
Решения зафиксированы ниже как обязательные к исполнению.

### В-1. Куда ставить программу (п. 1) — ✅ РЕШЕНО: вариант ниже утверждён

ТЗ: «минимизируем зависимость от админских прав», «ПО должно работать без
админских прав», и одновременно «ставиться в `C:/Program Files/...` и **там
хранить все конфиги, csv и графические темп-файлы**».

Так нельзя: запись в `Program Files` без прав администратора невозможна.
Программа установится (инсталлятор один раз попросит UAC), но при первом же
сохранении CSV упрётся в отказ доступа — либо молча уедет в
`VirtualStore` (Windows UAC-виртуализация), где пользователь их не найдёт.

**Рекомендую** (и заложу в план по умолчанию): раздельные пути, стандарт Windows —

| Что | Куда | Права |
|---|---|---|
| exe, `_internal/`, эталонные конфиги приборов | `%LOCALAPPDATA%\Programs\Legoshi\IDM\IVTrace` | **не нужны** |
| конфиги приборов (правленые), настройки приложения | `%LOCALAPPDATA%\Legoshi\IDM\IVTrace\config` | не нужны |
| CSV/XLSX/PNG — рабочая папка | по умолчанию `%USERPROFILE%\Documents\IVTrace`, настраивается из UI (п. 23) | не нужны |
| кеш, temp-графика | `<рабочая папка>\Cache` (по п. 23) | не нужны |

Установка целиком в пользовательский профиль → **инсталлятор вообще не просит
UAC**, автообновление (п. 2) работает без прав, что для апдейтера критично.
Вариант «Program Files для бинарников + LOCALAPPDATA для данных» тоже рабочий,
но требует UAC на установку и на каждое обновление.

### В-2. п. 3 — метаданные поверки в файлы результата — ✅ РЕШЕНО

Догадка подтверждена. В шапку CSV и на лист «Мета» XLSX пишется по каждому
использованному прибору:

```
# Прибор: <модель>, S/N <серийный>, VISA <ресурс>
#   поверка: <дата последней>, следующая: <дата следующей>
```

То есть **три факта на прибор**: что использовался, когда поверен, когда
следующая поверка. Дата следующей вычисляется из даты последней + межповерочный
интервал (оба поля — в JSON прибора).

### В-3. п. 19 — направления промера — ✅ РЕШЕНО

Пресеты с картинкой-схемой утверждены (вместо 8 галочек). Направление — это
три независимые оси, а не 4 варианта:

1. **направление внутри ветви**: от нуля к максимуму (`0→100`) или от максимума
   к нулю (`100→0`);
2. **порядок ветвей**: сначала «+», потом «−», или наоборот;
3. **стык ветвей**: ветви «расходятся от нуля» (`0→+100`, затем `0→−100`) или
   **«сходятся в нуле»** (`+100→0`, затем `0→−100`) — второй режим и есть
   непрерывный проход через ноль без скачка, в DTCal он сделан специально,
   чтобы не перемагничивать датчик (там прямо в описании репозитория:
   *branches meet at zero to respect sensor magnetization*).

2×2×2 = 8 комбинаций. В UI — **именованные пресеты с картинкой-схемой**.

**Обязателен к включению пресет `+100→0, затем 0→−100`** — непрерывный проход
через ноль без скачка (ветви «сходятся в нуле»). Это прямое требование
заказчика; в DTCal он же сделан специально, чтобы не перемагничивать датчик.

Предварительный список пресетов (финализируется в Ф2):

| Пресет | Схема | Зачем |
|---|---|---|
| Расходящийся от нуля | `0→+100`, затем `0→−100` | текущее поведение v1.4ae |
| **Сходящийся через ноль** | `+100→0`, затем `0→−100` | **обязательный**, непрерывный проход без скачка |
| Спад от максимума | `+100→0`, затем `−100→0` | обе ветви от максимума |
| Полный гистерезисный цикл | `0→+100→0→−100→0` | снятие петли гистерезиса |

### В-4. п. 10 — округление коэффициента — ✅ РЕШЕНО

Шаг 50 как в ТЗ. Рядом с округлённым значением **всегда показывается
фактическое и процент расхождения**, чтобы оператор видел, если округление
притянуто за уши (для малых коэффициентов шаг 50 грубоват: между 1:50 и 1:100
ничего нет).

**Автоматическое определение коэффициента помечается BETA** — по решению
заказчика. В UI и в доке — явная пометка.

### В-5. п. 28 — источник тока — ✅ РЕШЕНО

Источник на стенде: **АКИП-1162-10-1020** (госреестр СИ 92879-24),
1 канал, **10 В / 1020 А**.

Два следствия, оба важные:

1. **Источник физически способен выдать 1020 А — больше, чем выдерживает
   реле (800 А).** То есть программный лимит п. 28 не «на всякий случай», а
   единственное, что стоит между оператором и сгоревшим реле. Реле —
   связывающее ограничение, а не источник.
2. **Потолок по напряжению всего 10 В**, а `V_limit` сейчас не проверяется
   вообще. Задание `V_limit` больше 10 В физически недостижимо и должно
   отсекаться на вводе.

Конфиг `instruments/current_sources/` получает поля `max_current` (1020.0),
`max_voltage` (10.0), корректные `model_name`/`keywords` и номер в госреестре.
Набор SCPI-команд менять не нужно: АКИП-1162 — это ребрендинг ITECH IT-M,
команды в текущем конфиге те же (в DTCal файл так и называется
`akip1162.json`, а внутри — ровно наш ITECH-профиль).

## 2. Сквозные архитектурные изменения

Это не отдельные пункты ТЗ, а то, без чего пункты не сделать чисто. Делается
в Ф1-Ф2 и дальше используется всеми.

### А-1. Ось «тип выхода датчика» (для п. 4, 35)

Сейчас код жёстко предполагает, что выход датчика — **ток**
(`dmm.measure_current()`, колонка `I_meas_A`). Вводится вторая ось, независимая
от типа возбуждения:

|  | выход: ток | выход: напряжение |
|---|---|---|
| **возбуждение: ток** | есть сейчас | п. 4 |
| **возбуждение: напряжение** | п. 5 (чинится) | п. 4 + 5, BETA |

Следствия: `Multimeter` получает режим (`current`/`voltage`) и грузит
соответствующий блок конфига; колонка результата становится `Y_meas` с
отдельной колонкой единиц; конфиги мультиметров получают **два** набора
команд/шкал. Конфиги из DTCal переносятся почти как есть.

### А-2. Планировщик развёртки (для п. 8, 17, 18, 19)

Сейчас развёртка считается прямо в цикле:
`num_steps = int(round((X_stop - X_start) / X_step)) + 1`, знак навешивается
параметром `sign`. Этого не хватит ни для одного из пунктов 8/17/18/19.

Вводится **чистая функция-планировщик** без железа:

```
plan_sweep(X_start, X_stop, X_step, branches, direction_preset, ...)
    -> [SweepPoint(x_set, branch, relay_state, is_zero, is_endpoint), ...]
```

Вся комбинаторика ввода, обход нуля, обязательные точки (0 и |конец|),
порядок ветвей и направления живут здесь. Измерительный цикл становится
тупым исполнителем плана. **Это ключевое решение всего v2**: планировщик
тестируется сотней быстрых юнит-тестов без приборов, а измерительный цикл
перестаёт быть местом, где прячутся баги комбинаторики.

### А-3. Единый «результат точки» вместо голого float (для п. 7, 9, 14, 29)

Точка перестаёт быть числом. `MeasuredPoint` несёт: все N сырых отсчётов,
какие отброшены и почему (первый по п. 29, переполнение, повтор по п. 9),
среднее, СКО, использованный диапазон, знаковую погрешность (п. 31), флаги
(«переполнение», «инверсия полярности» п. 14, «превышен порог» п. 7).
CSV/XLSX и график берут из этой структуры то, что им нужно.

### А-4. Служба приборов, отвязанная от измерения (для п. 11, 12, 13, 25, 3)

Поиск приборов, их состояние, статус поверки, blink, ручное управление реле
выносятся в отдельный асинхронный сервис с собственным жизненным циклом,
не привязанный к запуску измерения. UI подписывается на его события.

### А-5. Пути и рабочая папка (для п. 1, 2, 23)

`apppaths.py` расширяется: `install_dir` / `config_dir` / `work_dir` / `cache_dir`
(см. В-1). Всё, что сейчас лезет в `data/`, идёт через эти функции.

### Ф2 — Ядро измерения · пункты 8, 17, 18, 19, 29, 9, 7, 14, 27

Строится на планировщике А-2 и структуре точки А-3. Всё это — один
взаимосвязанный кусок, дробить его нельзя.

| № | Что | Ключевое |
|---|---|---|
| **17** | Универсальный ввод | Планировщик А-2 принимает любые `X_start`/`X_stop` (`−250→250`, `0→250`, `250→−250`, `−25→25`, …) и раскладывает их на ветви + состояния реле. Источник не умеет отрицательный ток — знак **всегда** отрабатывается реле, никогда источником. Ноль измеряется всегда, если пересекается, даже если не попадает на шаг. Модуль конечной точки — тоже всегда. |
| **18** | Баги шага | Проверяется на планировщике юнит-тестами: шаг через ноль, шаг не кратный диапазону, `X_step` больше диапазона, накопление ошибки float на длинных развёртках (сейчас `int(round(...))` + умножение — на 0.1-шагах даст дрейф). |
| **8** | Выбор ветви | Не bool `use_relay`, а перечисление **`+` / `−` / `both`** (третье значение — «без реле», если оператор коммутирует руками). Заменяет кривой `use_relay` из ветки deepseek. |
| **19** | Направления промера | Пресеты направлений (см. В-3), реализуются как параметр планировщика. |
| **29** | Усреднение | Настраиваемое число отсчётов (**по умолчанию 4**), задержка между ними (по умолчанию 0), **отбрасывание первого отсчёта** (по умолчанию вкл). |
| **9** | Контрольные промеры | При отклонении сверх порога — ещё 2 попытки (итого 3). Стабильно мимо → точка бракуется и **не идёт в расчёт**, но остаётся в сырых данных с флагом. |
| **7** | Отсечка по погрешности | Переработка того, что пришло из ветки deepseek: галочка вкл/выкл, работает **после** механики п. 9 (три попытки → и только потом решение об остановке). |
| **14** | Ошибка ориентации/подключения | Подаём «+», на выходе «−» (и наоборот) → уведомление о перепутанной полярности/неисправности датчика. **На точку X=0 не распространяется** (там знак не определён). |
| **27** | Рост охлаждения с током | Задержка охлаждения растёт с током. Алгоритм — предположительно ∝ I² (джоулево тепло) с потолком; подключается галочкой, помечается **BETA**. |

**Риск: высокий** (много комбинаторики), но **проверяемо без железа** — в этом

Не копить всё до одного релиза v2.0 — на 36 пунктах это гарантированный
способ получить неотлаживаемый ком. Предлагаю:

  (заработают датчики напряжения, починится ранжирование), тестируется на стенде.

- **v2.0** после Ф6 — полный комплект с инсталлятором и автообновлением.

Каждая фаза — отдельный набор коммитов в `v2-dev`, тест-сьют зелёный на
каждом шаге, в `main` не льём до v2.0-alpha.
